# 架构重构实施方案

本方案用于指导星露谷游戏伴侣的源码重构。实施分批进行，每批都能从干净克隆构建和验证。具体顺序、依赖和完成条件维护在 [重构 TODO](architecture-refactor-todo.md)。

│   │   │   ├── adapters/

├── resources/
│   └── agent/

## 运行边界和依赖方向

| 边界 | 职责 | 传递的数据 |
| --- | --- | --- |
| WPF → Python | WPF 管理启动设置和自己启动的进程，通过本地 HTTP 提交请求及接收事件。 | 玩家指令、控制请求、查询、状态和回执展示数据 |
| Python → SMAPI | 运行时协调任务并提交动作，Mod 在主线程操作游戏。 | 存档身份、游戏会话身份、观察、动作请求和最终回执 |
| Python → 模型客户端 | 运行时选择后端和原会话，适配器负责进程、消息协议、取消和用量解析。 | 已限定的游戏上下文、可用工具、结果和用量回执 |
| 游戏内入口与 MCP → 运行时 | 游戏内聊天进入同一回合服务，MCP 在已有回合和权限范围内调用游戏操作。 | 玩家要求、当前回合授权、工具参数和执行结果 |

Python 的 `domain/` 持有任务和回执规则，`application/` 按这些规则协调回合与工作，并定义它需要的后端、游戏连接和存储接口。具体 HTTP、WebSocket、MCP、模型客户端、文件存储由 `adapters/` 实现。宿主启动时组装这些依赖。

桌面配置由 WPF 管理，伙伴的工作、偏好、记忆和会话绑定沿用现有持久化规则，游戏存档与游戏中已经发生的结果由游戏持有。原伙伴的角色配置和记忆继续由所选会话提供。

## 核心迁移

1. **记录现有行为并归位。** 在移动项目之前记录基线构建和关键用例。建立新的组件、资源和契约路径，先通过打包映射复用现有可运行链路，再从绿色包中跑通「桌面启动 → 加载隔离存档 → 提交指令 → 执行动作 → 展示回执」。
2. **提取共用运行时服务。** 从 `ChatBridge` 逐步提取回合执行、会话恢复、上下文和结果投递。让桌面通过应用服务提交指令、暂停、改派、查询和重连，逐步取消 `DesktopBridge` 对 `ChatBridge` 的继承和内部状态访问。拆分过程中每项业务规则以一个实现为准。
3. **迁移模型适配和持久化。** 沿用现有模型注册表，把各模型 CLI、会话协议、专属脚本及用量解析归入对应适配器。再梳理任务、记忆和会话绑定的读写边界，用旧数据读写和中断续跑测试验证兼容性。
4. **收敛宿主职责。** 在桌面内拆分 WPF 事件、HTTP 客户端、进程生命周期与设置。在 Mod 内将 `ModEntry` 收敛为 SMAPI 事件接线，把读档、控制权、观察和动作执行交给所属模块。
5. **验收与切换。** 从干净克隆构建新包，验证桌面和源码调试入口、旧数据迁移、同一原会话恢复、隔离实机以及回退。确认调用方已迁移后，再移除淘汰的模块和脚本。

## 需要守住的兼容边界

| 项目 | 本轮重构的约束 |
| --- | --- |
| 启动与发行 | 绿色包根目录放置自包含的 `星露谷游戏伴侣.exe` 和使用说明。`Mods/` 存放配套 Mod 与 Python，`docs/` 存放更新日志和许可。源码调试与隔离验收保留游戏内启动路径。 |
| 现有调用方 | 盘点 WPF 启动参数、`python -m stardew_ai_runtime.*`、PowerShell 调试入口、CI 和打包校验。迁移中同步更新调用，仍有使用方的旧入口由薄转发器承接。 |
| 跨进程契约 | 保持本地 HTTP `/v1`、现有 WebSocket 消息和八个具名游戏工具的行为。保留鉴权、存档与游戏会话隔离、请求关联和原生回执。先建立契约测试，再按实际需要单独评审协议变更。 |
| 旧配置和数据 | 保留 SMAPI `UniqueID`、现有配置和数据格式，以及旧安装识别规则。继续支持旧绿色包与旧 Mod 的数据导入、Pi 会话接续和中断后继续导入。旧包可用于回退，切换前由玩家确认并保存退出。 |
| 会话与上下文 | 同一角色维持一个执行中的会话。读档重建世界上下文，同一游戏内重连沿用原会话。原会话不可用时明确报错并保留绑定。状态增量以已确认送达为基线。 |
| 派工与控制权 | 聊天、工作、改派共用回合和执行规则。暂停与 F9 接管在工具执行时检查。改派先核对旧动作的终态或当前状态，成果按原生回执保留。游戏动作保持即时执行和复查。 |
| 资源与打包 | `resources/agent/` 是生产提示词和工具指导的源码位置。安装位置由打包层映射。加载器、Python 与 PowerShell 校验、MCP 注册脚本使用一致的资源路径和清单。包内保留项目与第三方许可。 |

八个具名游戏工具以现有注册集合为准：`get_status`、`query_game`、`submit_work`、`manage_arrangements`、`remember`、`request_player_decision`、`consult` 和 `read_reload_history`。跨语言契约检查沿用单一生成来源。

实施时分别定位源码仓库、解压包和存档数据目录。路径来自现有入口传入的运行目录或发布文件映射，避免依赖源码文件固定的父目录层数。第一批可继续使用已发行包内部路径，在所有调用方迁移后再评估包内路径优化。

## 验收方法

| 验收 | 通过条件 |
| --- | --- |
| 构建与离线检查 | 从干净克隆执行当前阶段文档给出的构建命令。相关 Python、C# 和跨语言测试通过。新包完整性校验通过，程序依赖、提示词和许可证齐全。 |
| 桌面与游戏联调 | 使用完整解压的绿色包、隔离存档和模拟模型。桌面启动、观察、指令、原生回执、暂停、接管、改派和重连均有可核对的结果。 |
| 会话与数据兼容 | 使用旧格式数据样本核对导入结果、存档隔离、断点续导及原会话接续。核对原安装数据和新安装导入结果，按导入测试覆盖冲突和失败恢复。 |
| 正式伙伴实机回归 | 使用正式 mcode 和隔离存档执行 `care-guidance`、`harvest-logistics`、`rest-forestry`。按原生结果、收集物、背包、移动碰撞和动画核验，单独注明真实模型的验收范围。[固定实机用例](../repeatable-companion-acceptance.md) |

每批提交附验证命令、结果和未执行项。当前构建与测试入口见[参与开发](../../CONTRIBUTING.md)，迁移后的入口在对应任务完成时同步更新。
