# 绿色包更新模块

## 桌面入口

「设置 → 关于与更新」显示安装包的发布标签。默认查询 GitHub Release 正式版，勾选「检查预览版」后只查预览版。界面显示发现的版本和发布说明，玩家分别确认下载和安装。切换发行通道时明确提示目标可能早于当前版本。

## 分阶段实现

| 阶段 | 实现 | 验收 |
| --- | --- | --- |
| 1. 本地更新 | 使用独立更新进程安装完整 ZIP。确认后关闭桌面和所属服务，在原目录替换清单内文件。 | 检查原目录启动，旧文件删除，启动失败和中断后恢复。 |
| 2. 在线更新 | 从固定的 GitHub 仓库查询发布，按通道过滤，下载 ZIP 和校验文件。实际发布标签区分同基础版本的多个包。 | 覆盖正式版、预览版、空通道、重复标签、下载失败和摘要不符。 |
| 3. 数据迁移 | 绿色目录继续作为默认数据位置。玩家可复制数据到独立目录、导入旧绿色包，或连接已有数据。保留 Windows 凭据所属的原目录标识。 | 检查 SQLite 与 WAL、插件、Mod 配置及伙伴资料，避免两个伴侣同时打开同一个独立数据目录。 |
| 4. 发布签名 | 官方 ZIP 使用 ECDSA P-256 对归档的 SHA256 签名，公钥嵌入桌面，私钥由 Release 工作流读取。 | 使用测试密钥安装签名包，验证错误签名和修改后的 ZIP 在应用前被拒绝。 |

## 安装事务

1. 校验发布签名、ZIP 摘要、包内清单和更新协议，解包到绿色包下的 `.updates`。Release 标签和通道须与包内元数据一致。
2. 玩家确认后，将授权绑定到已校验的清单，再退出桌面并交接给更新器。更新器按 PID 和启动时间等待桌面退出，重新确认游戏已退出，锁定安装和数据目录。
3. 从暂存目录启动新版桌面并检查界面能否构建。通过后备份现有程序及用户数据，写入事务日志，再替换受管文件。安装后的桌面加载设置并验证内置 Node、SQLite 与模型目录。
4. 自检成功后从原启动路径重新打开，保留最近一次成功更新的备份。自检失败恢复旧文件。中断后再次打开桌面会继续恢复。

## 发布和首次过渡

生产 Release 附带 ZIP、`.sha256` 和 `.sig`，签名格式为 64 字节 IEEE P1363。采用 .NET 内置的 ECDSA P-256，发行人可用 PowerShell 生成密钥。私钥导出仅用于设置 GitHub Secret，始终保存在发布者控制的安全位置。

```powershell
$key = [Security.Cryptography.ECDsa]::Create([Security.Cryptography.ECCurve+NamedCurves]::nistP256)
# 公钥 Variable 的值
[Convert]::ToBase64String($key.ExportSubjectPublicKeyInfo())
# 在受控环境把 $key.ExportPkcs8PrivateKey() 的 Base64 编码保存为 Secret
$key.Dispose()
```

已经安装的旧版可以在首次更新时解压到另一个目录，并从新版界面导入旧包。后续更新沿用原路径。无公钥的本地构建可用本地 ZIP 做开发验收，官方在线查询只在包含可信公钥的构建中启用。

发布工作流在上传制品前调用更新器使用的同一套验证代码，检查签名、归档摘要、文件清单与发布标签和通道。持有 ZIP、两个校验文件和发布公钥时，可在本地运行同一项检查。

```powershell
dotnet run --project tests/desktop-updates -c Release -- --verify-release '<发行 ZIP>' '<SPKI 公钥文件>' '<Release 标签>' preview
```

## 验收记录

- 两份 Windows 绿色包使用测试密钥验签并通过桌面界面完成原目录升级。不能启动的 EXE 在替换前被拒绝。故意让新版 Node 自检失败后，更新器恢复原版本并重新打开，设置、数据库与 WAL、插件和 Mod 数据的文件摘要一致。
- 通过桌面界面迁移到独立数据目录，重新打开后读取同一 Windows 用户的原模型凭据。旧绿色包导入、重复打开独立数据目录、损坏签名和中断事务覆盖在 `tests/desktop-updates`。
- 正式版与预览版使用模拟资产完成发现和下载测试。公开链路验收需要同一生产密钥签出的两个预览版。把第一个 ZIP 解压到隔离目录并打开，勾选「检查预览版」，检查、下载并安装后发布的版本，确认桌面从原路径重启并显示新标签。
