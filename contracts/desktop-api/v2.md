# 桌面 API v2

WPF 启动随包 Node，本地服务监听 `127.0.0.1`，通过标准输出公布端口和协议版本 `2`。每次启动由宿主生成独立的 Bearer 凭据。启动信息、请求和事件使用 UTF-8 JSON。WPF 遇到版本不匹配时停止本次启动并报告错误。

| 路由 | 行为 |
| --- | --- |
| GET `/v2/status` | 读取当前绑定、角色控制权、工作和模型状态。 |
| GET `/v2/events` | SSE 投递绑定变化、接收、进度、回复、动作回执和待确认事项。使用事件 ID 进行断线续读，缓冲过期时重取状态。 |
| POST `/v2/model/test` | 测试指定服务商与模型能否发出工具调用、读取工具回执并返回确认文本。可在读档前执行。API Key 通过已鉴权的本地请求交给运行时，仅在内存持有。 |
| GET `/v2/model/providers`、POST `/v2/model/configure` | 获取运行时支持的服务商目录，建立游戏回合使用的模型上下文。配置请求使用 `selection` 和 `apiKey`。 |
| POST `/v2/commands` | 提交自然语言，包含 `requestId`、`saveId`、`gameSessionId`、`text`、`mode`（`send` 或 `interrupt`）及可选的 `decisionId`。接收返回 202，重复提交返回已有记录。 |
| GET `/v2/commands/{requestId}` | 查询指令接收与执行状态。 |
| POST `/v2/plugins/submit`、`/v2/plugins/query`、`/v2/plugins/close` | 桌面插件宿主传入已鉴别的插件 ID。运行时受理独立指令、按插件查询 SQLite 记录，以及关闭运行实例并取消该插件的活动回合。公开端点与字段见插件宿主契约。 |
| POST `/v2/control` | 暂停、继续、取消、玩家接管、交权、核对旧动作，或 `action: "observe"` 刷新游戏观察（不派工、不交权）。 |
| POST `/v2/profile`、`/v2/memory`、`/v2/history`、`/v2/messages` | 当前存档的伙伴数据与对话。编辑携带期望修订号。 |
| POST `/v2/notices`、`/v2/initiative`、`/v2/milestones`、`/v2/usage` | 玩家选择、自动续作配置、计划和用量。全局用量查询可省略游戏绑定。 |

存档相关请求和事件携带 `saveId`、`gameSessionId`。工作进度可关联 `requestId`、`turnId` 和 `actionId`。接收回执只确认入站，动作终态来自 Mod。等待旧动作期间展示待核对状态，暂停派工。

状态可含 `gameDate`、`timeOfDay` 和活动回合的 `pluginSource`。本机插件只能访问宿主重新生成的公开投影。 [插件宿主 v1 契约](../plugin-host/v1.md)

`activeSkillId` 表示当前正在请求的原生能力，用于中文活动提示。`work.recentExecutions` 提供最近 40 条结构化记录，包含动作编号、游戏会话、日期、能力、终态、可空的计数、原因码和 `playerActionRequired`，不预先拼接工具名与英文状态摘要。`workContext` 的 `goalId`、`requestId`、地点与目标来自程序绑定，并在原生动作开始前保存，以便重连核对后仍能关联工作；旧记录缺少关联时单独展示。该关联只记录已发生动作的归属，不是工作队列。

`agentPhase` 与 `work.activity.phase` 共享阶段。可取 `thinking`、`model-retry`、`model-error`、`planning-route`、`validating`、`executing`、`verifying`、`waiting-game`、`waiting-receipt`、`reconciling`、`unresolved`、`stopping`、`needs-player`、`paused`、`player-control` 或 `idle`。原生阶段只采信匹配当前动作编号的 `actionPhase`。

模型请求等待重试时，`modelIssue` 提供 `code`、`message`、`attempt` 和 `maxAttempts`。模型请求最终失败时，`modelIssue` 保留原因，失败回复可携带 `errorCode`。

回执投影增加 `recordedAt` 和 `evidence.quantities`（`kind` 与正整数 `value`）；数量来自原生效果或物品明细，不从完成目标计数推算。背包变化与收集明细只取一份，原始回执不变。动作上下文增加开始时的 `gameDate`、`turnId`、`triggerRequestId`；原要求由 `requestId` 保留，补充要求按实际送达边界记录来源。`recovery` 事件可含已核对的 `receipt`，未收到终态时不返回零产出。

桌面将普通回执汇入一条「最近进展」，按目标、日期和工作类型展示摘要，工作过程默认折叠；需要玩家处理或结果未知时保留明确提示。重复失败仅在同一会话、请求、目标、日期、动作、落点和原因一致且连续出现时合并显示。完整原生回执继续保存在运行时，模型与控制权判断使用原始结果。共享展示边界样例见 [work-feedback.json](examples/work-feedback.json)。

SSE 历史补发、实时事件和心跳共用一个有序写入器。`write(false)` 表示帧已进入缓冲，等待 `drain` 后发送下一帧；每连接最多积压 8 MiB／512 条排队帧，30 秒不排空时关闭该订阅并允许客户端按游标恢复，心跳不加入积压。

桌面仅在收到完整 SSE 帧并交付后推进 `Last-Event-ID`。推送断开时客户端本地生成 `desktop.connection`（`payload.status: "reconnecting"`），保留原游戏绑定、页面和草稿，不伪造 `status.ready: false`；收到权威 `status` 后恢复操作。该本地通知不表示游戏或模型服务已退出，也不授权自动重发指令。

模型 `selection` 使用 `provider`、`model`、可选的 `reasoning` 和 `stream`。流式开关缺省为 `true`，`false` 时等待完整 JSON。OpenAI 官方使用 Responses，DeepSeek 官方使用 Chat Completions，地址由预设固定。

自定义接口使用 `provider: "custom"`，携带 `protocol: "chat-completions"` 或 `"responses"`、HTTPS `baseUrl` 和网关的模型 ID。Base URL 保留接口前缀，运行时拼接协议路径。历史 `openai-compatible` 配置按 Responses 解析。目录返回每个入口的默认协议、流式开关、默认模型和模型能力。

响应区分未鉴权（401）、参数无效（400）、版本或当前游戏状态冲突（409）、无法确认（503）。面向用户的错误只含可处理的原因，密钥、请求头和厂商原始错误不进入日志或桌面事件。[游戏传输契约](../game-bridge/v2.md)
